### The architecture (worth reusing)

- **Ankles are judged from the AUTHORED pose, never the stabilized skeleton.** The proxy
  publishes `AnimatedLeft/RightFootCS` captured *before* any IK is applied, in
  `PostEvaluate` (game thread). Feeding the solver its own output would make a held foot
  look permanently grounded, so it could never be released and the leg would drag until
  the hip tore it off the mark. This is the single most important design decision here.
- **Two-bone IK, not FABRIK/full-body.** `AnimationCore::SolveTwoBoneIK(Thigh, Calf, Foot,
  JointTarget, Effector, /*bAllowStretching=*/false, 1, 1)` per leg. Note the transform
  overload's 4th arg is the **pole/plane target** (`JointTarget`), derived from the current
  knee offset so the authored bend direction survives; stretching is OFF, so an unreachable
  mark falls short instead of pulling the leg apart.
- **Marks are weight-ramped, never switched.** `LockAlpha` is `FInterpTo`-filtered (18 in /
  24 out); a new mark is only taken once the old one has faded below 0.25.
- **Release is by knee reach (94% of leg length) or authored lift-off (>8 cm clearance).**
  Lift-off is checked at every speed so turning on the spot still picks the feet up.
- **Ankle height is measured, not assumed**: composed from the mesh's own reference pose
  (`C26_CHARACTER_ANKLE_HEIGHT mesh=... height=8.65cm` for `SK_C26_Athlete_Review`).
- **Ground is a cached trace** (refresh every 0.25 s or 25 cm of travel).
- **Perf gates**: skipped entirely when hidden, `GetPredictedLODLevel() > 1`, or
  `Quality == Low`; the proxy also early-outs before the `FCSPose` work when no lock is
  active. `FCSPose::InitPose` + `ConvertComponentPosesToLocalPoses` is the real cost.

### Defect I found and fixed (the one substantive change I made)

The pelvis compensation was **inverted relative to its own comment**. It computed
`FMath::Min(0, AnimatedZ - PlantedAnkleZ)`, which drops the hips exactly when the mark sits
*above* the animated ankle (the case that needs nothing — the solver reaches it by bending)
and does nothing when the mark sits *below* it (the only case that can pull the leg
straight). Changed to `-FMath::Max(0, AnimatedZ - PlantedAnkleZ)`. Clamp stays [-6, 0] cm.
Also corrected the on-screen debug string, which still asserted `RuntimeIK:off`; it now
reports live `FootIK` / `Lock:L… R…` / `Pelvis` weights so an in-match capture can prove
the solver engaged.

### Performance: the desktop frame-time numbers are unusable here

`C26_GATE_FRAME_TIME` means looked like a real regression (base 40.5 ms vs two runs of the
task build at 64.6 / 63.4 ms), and the two task runs agreed with each other, which is
exactly what a real cost looks like. It is not one. `uptime` showed a **load average of
~34.6 on a 10-core machine** — `CRICKET26-Worktree-1..4` all exist and the other Round 3
agents were running UE in parallel. `GateFrameTimes` is sampled per tick over
RunUp/Delivery/InPlay, so a contended machine inflates both the mean and the sample count
(629 vs 762/781) simultaneously.

**Rule: never quote `C26_GATE_FRAME_TIME` while other worktrees are active. Check `uptime`
before believing any frame-time delta.** (`ps` is blocked by the sandbox, but `uptime`
works.)

What the design actually guarantees, and is worth keeping:
- two-bone IK on **two legs only** — not a full-body solver;
- skipped when `!Body->IsVisible()` or `GetPredictedLODLevel() > 1` (the LOD gate is the
  real distance control, driven by `SetQualityForView`);
- the proxy returns **before** `FCSPose::InitPose` when no lock is active, so the expensive
  part is only paid while a foot is genuinely planted;
- ground trace cached (0.25 s / 25 cm).

**Gap worth reporting:** `Quality == EC26CharacterQuality::Low` is an intended hard bypass
but is currently **unreachable** — `Quality` is defaulted to `High` in the header and
nothing ever assigns it. `C26MatchGameMode` drives `Venue->SetQuality(Preferences->Quality)`
and `AC26Athlete::UpdateDetail` only calls `Presentation->SetQualityForView(ViewPoint)`,
which sets LOD but not `Quality`. So the mobile tier does not propagate to the presentation
component today. Not fixed here (it crosses into the preferences path); the LOD gate covers
distance culling in the meantime.

### Trap: `FMath::FInterpTo` is NOT exponential

I asserted a 90° snap would absorb to `-90 * exp(-14*0.016)` ≈ -71.9 and it failed. `FInterpTo`
is **linear-alpha**: `Current + (Target-Current) * Clamp(DeltaTime*InterpSpeed, 0, 1)`, so one
frame at 16 ms takes 22.4% of the remaining distance → -69.8. Consequences:
- the test now asserts the **fraction** absorbed (≥75%), not an absolute value;
- the unwind is geometric at 22.4%/frame, so <0.5° is reached in 20 frames (320 ms);
- at very low frame rates `DeltaTime*InterpSpeed` clamps to 1 and the filter completes in a
  single frame — fine for a yaw lag, but worth knowing for the foot-lock ramps (18/24), which
  behave the same way below ~18 fps.

The comment in `UpdateOrientationSmoothing` claiming a "71 ms time constant" was wrong for the
same reason and now reads "~0.3 s at 60 Hz, under a tenth left after ~145 ms".

Measured: `Transitions: 12 speeds inside the band; a 90deg re-aim absorbs to -69.8deg (78%) in
one frame and unwinds to <0.5deg in 20 frames (320ms)`. `Cricket26.Characters` is 8/8.
