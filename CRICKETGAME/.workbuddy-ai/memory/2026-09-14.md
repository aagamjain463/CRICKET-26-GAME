### What was already there when I picked it up

### The architecture (worth reusing)

- **Ankles are judged from the AUTHORED pose, never the stabilized skeleton.** The proxy
  publishes `AnimatedLeft/RightFootCS` captured *before* any IK is applied, in
  `PostEvaluate` (game thread). Feeding the solver its own output would make a held foot
  look permanently grounded, so it could never be released and the leg would drag until
  the hip tore it off the mark. This is the single most important design decision here.
- **Two-bone IK, not FABRIK/full-body.** `AnimationCore::SolveTwoBoneIK(Thigh, Calf, Foot,
  JointTarget, Effector, /*bAllowStretching=*/false, 1, 1)` per leg. Note the transform
  overload's 4th arg is the **pole/plane target** (`JointTarget`), derived from the current
  knee offset so the authored bend direction survives; stretching is OFF, so an unreachable
  mark falls short instead of pulling the leg apart.
- **Marks are weight-ramped, never switched.** `LockAlpha` is `FInterpTo`-filtered (18 in /
  24 out); a new mark is only taken once the old one has faded below 0.25.
- **Release is by knee reach (94% of leg length) or authored lift-off (>8 cm clearance).**
  Lift-off is checked at every speed so turning on the spot still picks the feet up.
- **Ankle height is measured, not assumed**: composed from the mesh's own reference pose
  (`C26_CHARACTER_ANKLE_HEIGHT mesh=... height=8.65cm` for `SK_C26_Athlete_Review`).
- **Ground is a cached trace** (refresh every 0.25 s or 25 cm of travel).
- **Perf gates**: skipped entirely when hidden, `GetPredictedLODLevel() > 1`, or
  `Quality == Low`; the proxy also early-outs before the `FCSPose` work when no lock is
  active. `FCSPose::InitPose` + `ConvertComponentPosesToLocalPoses` is the real cost.

### Defect I found and fixed (the one substantive change I made)

The pelvis compensation was **inverted relative to its own comment**. It computed
`FMath::Min(0, AnimatedZ - PlantedAnkleZ)`, which drops the hips exactly when the mark sits
*above* the animated ankle (the case that needs nothing — the solver reaches it by bending)
and does nothing when the mark sits *below* it (the only case that can pull the leg
straight). Changed to `-FMath::Max(0, AnimatedZ - PlantedAnkleZ)`. Clamp stays [-6, 0] cm.
Also corrected the on-screen debug string, which still asserted `RuntimeIK:off`; it now
reports live `FootIK` / `Lock:L… R…` / `Pelvis` weights so an in-match capture can prove
the solver engaged.

### Performance: the desktop frame-time numbers are unusable here

`C26_GATE_FRAME_TIME` means looked like a real regression (base 40.5 ms vs two runs of the
task build at 64.6 / 63.4 ms), and the two task runs agreed with each other, which is
exactly what a real cost looks like. It is not one. `uptime` showed a **load average of
~34.6 on a 10-core machine** — `CRICKET26-Worktree-1..4` all exist and the other Round 3
agents were running UE in parallel. `GateFrameTimes` is sampled per tick over
RunUp/Delivery/InPlay, so a contended machine inflates both the mean and the sample count
(629 vs 762/781) simultaneously.

**Rule: never quote `C26_GATE_FRAME_TIME` while other worktrees are active. Check `uptime`
before believing any frame-time delta.** (`ps` is blocked by the sandbox, but `uptime`
works.)

What the design actually guarantees, and is worth keeping:
- two-bone IK on **two legs only** — not a full-body solver;
- skipped when `!Body->IsVisible()` or `GetPredictedLODLevel() > 1` (the LOD gate is the
  real distance control, driven by `SetQualityForView`);
- the proxy returns **before** `FCSPose::InitPose` when no lock is active, so the expensive
  part is only paid while a foot is genuinely planted;
- ground trace cached (0.25 s / 25 cm).

**Gap worth reporting:** `Quality == EC26CharacterQuality::Low` is an intended hard bypass
but is currently **unreachable** — `Quality` is defaulted to `High` in the header and
nothing ever assigns it. `C26MatchGameMode` drives `Venue->SetQuality(Preferences->Quality)`
and `AC26Athlete::UpdateDetail` only calls `Presentation->SetQualityForView(ViewPoint)`,
which sets LOD but not `Quality`. So the mobile tier does not propagate to the presentation
component today. Not fixed here (it crosses into the preferences path); the LOD gate covers
distance culling in the meantime.

## Round 3 Task 4, continuation — PART B/C automated coverage

The task asked to test idle→movement, movement→idle and action→recovery, but PART B and
PART C had no coverage: the rules were inline in `SelectState` and
`UpdateOrientationSmoothing`, both of which need a live `AC26Athlete`. Rather than build an
athlete in a test, the pure rules were **extracted** (behaviour-preserving) into a
`C26Presentation` namespace declared in `C26CharacterPresentationComponent.h`:

| Function | What it encodes |
|---|---|
| `WantsMove(bWasMoving, GroundSpeed)` | the hysteresis band |
| `TransitionSpent(Transition, GroundSpeed, TransitionAge)` | when Start/Stop hands back |
| `StepMeshYawOffset(Offset, YawDelta, Dt)` | one frame of the mesh-only yaw lag |

`inline constexpr` tuning constants (StartSpeed/StopSpeed/LegReach/LiftHeight/
OrientationSnapDegrees/MaxMeshYawLag) moved into the same namespace so each number has one
home. `SelectState` and `UpdateOrientationSmoothing` now call these; the diff is a pure
move of the same expressions. `StateAllowsFootLock` was made **public** so the scope
boundary (only shared locomotion/stance clips may be foot-locked) is assertable.

New test `Cricket26.Characters.LocomotionTransitions` covers the band (12 speeds, each
asserted to hold its current state), the Start/Stop exit rules, that turn clips always play
out, the orientation snap absorption and unwind, and that batting/bowling/fielding action
clips are never foot-locked.

### Trap: `FMath::FInterpTo` is NOT exponential

I asserted a 90° snap would absorb to `-90 * exp(-14*0.016)` ≈ -71.9 and it failed. `FInterpTo`
is **linear-alpha**: `Current + (Target-Current) * Clamp(DeltaTime*InterpSpeed, 0, 1)`, so one
frame at 16 ms takes 22.4% of the remaining distance → -69.8. Consequences:
- the test now asserts the **fraction** absorbed (≥75%), not an absolute value;
- the unwind is geometric at 22.4%/frame, so <0.5° is reached in 20 frames (320 ms);
- at very low frame rates `DeltaTime*InterpSpeed` clamps to 1 and the filter completes in a
  single frame — fine for a yaw lag, but worth knowing for the foot-lock ramps (18/24), which
  behave the same way below ~18 fps.

The comment in `UpdateOrientationSmoothing` claiming a "71 ms time constant" was wrong for the
same reason and now reads "~0.3 s at 60 Hz, under a tenth left after ~145 ms".

Measured: `Transitions: 12 speeds inside the band; a 90deg re-aim absorbs to -69.8deg (78%) in
one frame and unwinds to <0.5deg in 20 frames (320ms)`. `Cricket26.Characters` is 8/8.

```bash
  -ExecCmds="Automation RunTests Cricket26.Characters; Quit" \
  -TestExit="Automation Test Queue Empty" -abslog="$PWD/Artifacts/<name>.log"
```

`grep -E "Authored |Planted |Solver:|Transitions:|Action hand-back"` for `AddInfo` lines.
Exit code is not a pass/fail signal — it is 3 when any test fails, 0 otherwise, but a
`Result={Fail}` line is the real evidence.

### The FootSkate assertion was measuring the wrong quantity

It required the two feet to agree on their dragged **rate** and failed at 25% tolerance.
Instrumenting first (rather than loosening the bound) showed why:

| Foot | Stance frames | Ground dragged per stance | Implied rate |
|---|---|---|---|
| Left | 18 | **49.97 cm** | 394 cm/s |
| Right | 13 | **49.58 cm** | 542 cm/s |

The **distance agrees to 0.8%**; the rate differs 38% only because the right contact is
sharper, so the same 3 cm stance band catches fewer frames. The rate was never the
invariant. Now asserted: distance per stance within 20% (tight, and the real property of a
valid cycle), rate only for gross sanity (both in 150-900 cm/s, within 3x).

**Reusable rule: for a walk/run cycle, the invariant between the two feet is the ground
distance covered per stance, not the speed.** Speed divides by a stance *duration* that
depends on how sharply the foot enters contact — an asset property, not a property of the
motion. Asserting rate makes the test fail on a good clip.

Also fixed: `Measure()` used a **shared average** stride speed for both feet, which
handicapped the faster foot's own measurement. Each foot now uses its own authored speed.

### Action -> recovery: the defect is a FROZEN outgoing pose

Not a blend that is too long — the action stopping dead at the switch frame, so the body
stalls for the whole blend. Extracted the two inline expressions (behaviour-preserving,
verified line by line) so they are assertable:

| Function | Was inline as |
|---|---|
| `AdvanceOutgoingPose(PreviousTime, Length, Dt)` | the `Fmod(Prev+Dt, PrevLength)` guard |
| `BlendWeight(BlendClock, BlendSeconds)` | `SmoothStep(0, Max(.02f, BlendSeconds), BlendClock)` |

`.02f` is now named `MinBlendSeconds`. `Cricket26.Characters.ActionRecovery` drives the
hand-back against real assets (`A_C26_FastBowl_R` 1.80s -> `A_C26_FielderReady`) starting
**two frames from the end of the action**, so the clip is forced to run out mid-blend —
the normal case for a delivery, and the case a "clamp at the last frame" implementation
would freeze on. Measured: outgoing pose advanced on **8/8 frames, 1 wrap**, no repeated
frame; blend eases in (first tenth moves 0.028 vs 0.148 in the middle).

Note: starting at 90% of the clip does **not** wrap (1.62+0.12 < 1.80), so the wrap branch
silently went untested until the start was made length-relative. Prefer a length-relative
start over a percentage when the point is to exercise the end-of-clip path.

### Knees: the requirement that had no coverage

The brief asks for "knees anatomically believable" and nothing asserted it. Knee inversion
is the classic two-bone failure — the pole target is derived from the *current* knee
offset, so a degenerate offset can put the joint on the wrong side of the thigh->ankle
line and the leg bends backwards, which reads worse than the sliding it was fixing.

Measure the knee's **perpendicular bulge** off the thigh->ankle line and require the
direction to survive:

```
Knee: authored bulge 18.83cm; worst direction agreement 0.99 across 5 marks;
      unreachable mark leaves 0.00cm
```

- **0.99 agreement** is the real result: deriving the pole from the current knee offset
  preserves the authored bend plane almost exactly. The knee neither flips nor wanders.
- An unreachable mark straightens the leg to **0.00cm** of bulge instead of inverting.
- **The authored standing leg is NOT near-straight** (18.83cm of bulge against
  45.4+42.2cm of leg) — I had assumed it would be, and the measurement corrected it. The
  `KneeDir.IsNearlyZero()` fallback is therefore not on the common path.

A mark can legitimately *flatten* the bend, so the assertion judges direction only once a
bulge >1cm exists; asserting on a near-zero bulge would be asserting on noise.

### Deliberately NOT fixed: `Quality == Low` is still unreachable

Re-examined and left alone. The chain is `C26MatchGameMode` ->
`Venue->SetQuality(Preferences->Quality)` (an `int` on `AC26Stadium`), while
`AC26Athlete::C26Athlete.cpp:217` calls `Presentation->SetQualityForView(ViewPoint)`, which
reads `Quality` for the LOD bias but never assigns it. Wiring it means changing
`SetQualityForView`'s signature or having the athlete query the stadium — i.e. touching
`AC26Athlete`/`AC26Stadium`, outside the shared presentation foundation, and the brief says
to commit only this task's files.

It is also **unvalidatable here**: a mobile benefit cannot be measured on a machine at load
average 15.6 with three sibling worktrees running UE. An unvalidated late change is worse
than a clearly reported gap, and the LOD gate already covers distance culling. Note also
that wiring it would make Low quality *disable* the foot stabilization entirely — the
intended perf trade, but worth knowing before "fixing" it.

## Round 3 Task 4e — proving the stabilizer actually runs in a match

The single most valuable verification of the whole task, and it started from a **misreading**.

### The trap: a debug overlay is not evidence

The character debug overlay (`c26.Character.Debug`) draws a per-athlete text block with live
`FootIK` / `Lock:L… R…` weights. In a gate screenshot one block appeared to read
`Role:2 Run Speed:690 ... FootIK:0.00 Lock:L0.00 R0.00` — i.e. **a bowler sprinting with the
stabilizer apparently doing nothing.** That would have been a serious finding: green unit
tests and an inert feature in the real match.

It was wrong. Debug strings are drawn at `ActorLocation + (0,0,210)` for ten athletes in one
frame, so the blocks **overlap and interleave** and cannot be attributed reliably. And the
weights are screen-only, so nothing in the log could confirm or deny it.

**Rule: never diagnose a per-entity value from overlapping debug strings in a screenshot.
Add a log line.** Two `UE_LOG`s under the existing debug CVar answered it in one gate run.

```bash
  -C26CharacterSlice -C26CharacterProfile=.../DA_C26_FielderReview \
```

What this settles that nothing else did:

1. **The stabilizer engages in a real match** — 232 marks in `Run` alone — and takes **zero**

2. **The perf gate is not dead code.** 44 of 54 skips are distance-driven (LOD 2/3 as athletes

`quality=2` (High) in every skip line is further confirmation that `Quality` is never assigned
— see the 4d note on why that is left reported.

### A one-shot latched diagnostic answers only the first frame

The first version logged the skip reason once per athlete, forever. It fired at frame 0 with
`visible=0` and then never again, which would have made "the stabilizer is skipped because the
body isn't visible" the permanent answer for a condition that was a startup transient.

Fixed by **re-arming the latch whenever the stabilizer runs**, so an athlete that *starts*
being skipped later reports its reason too. That changed the count from 10 to 54 and revealed
the LOD gate as the real cause. If a diagnostic is one-shot, make it one-shot **per state
transition**, not per process.

Also worth knowing: `ReviewPremiumCharacter.sh` cannot verify any of this. `AC26CharacterReviewMode`
drives `UC26CricketerAnimInstance` **directly** and never creates or ticks
`UC26CharacterPresentationComponent`, so `FootIKWeight`/`LockAlpha` stay at their defaults and
the foot IK is inert in review captures. Only the `-C26CharacterSlice` match path exercises it.
