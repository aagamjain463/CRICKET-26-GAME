## Bowling control loop — rebuilt and verified

Rebuilt the touch-first bowling loop so the player authors a delivery end to end
(type → exact pitch target → movement direction → amount → pace → run-up → release
bar → composed ball). Reference doc: `Docs/BOWLING_CONTROL_SYSTEM.md`.

### Two real defects found, not just harness bugs

1. **The tree did not compile as handed over.** `C26HUD.cpp::DrawBowlingTarget()`
   referenced `bBowlingCharging` / `BowlingChargeStart` / `BowlingChargeCurrent` /
   `BowlingEffort` — members of a bowling-charge model that had already been deleted.
   Rewritten to read `PacePointerId` and `BowlingPlan.PaceNormalized`.
2. **Reverse swing was a no-op.** `FC26BowlingTuning::ReverseOnsetFrac` is documented
   as a *fraction of the flight* but `FC26Simulation::Integrate` compared it to
   `S.Age` in **seconds**. Flight to the pitch is ~0.38 s and the constant was 0.55, so
   the acceleration never applied. `Release()` still trimmed the launch as though it
   had, so a reverse swinger pitched ~10 cm short of target on the wrong line. Fixed by
   resolving the fraction against the real flight time in `Release()`, and by trimming
   the launch with `C26Delivery::SwingDeflection()` — the same curve the integrator
   uses. `MaxReverseAccel` raised 265 → 1080 to compensate for the shorter integration
   window.

### Key measurement insight (reusable)

`FC26Simulation::Release()` trims the launch velocity so the ball still pitches **on
the aim point**. So comparing where two plans pitch measures the *aim*, not the
movement — the original lab compared bounce-X and read ~0 for every swing delivery.
The correct technique: re-integrate the delivered plan twice, strip the movement from
one, then give the stripped ball the **identical launch** (`Without.Ball.Velocity =
With.Ball.Velocity`) and sample `Predict(t)` at the same instants. Also:
`Release()` leaves `Ball` at the *release* state (it integrates a local copy), so
`Predict(seconds)` walks the real trajectory.

### Other changes

- Around the wicket now actually moves the release point (`CreaseOffsetCm()`), and the
  trajectory preview shares it.
- Steerable stock ball raised 0.22 → 0.55 of `MaxSwingAccel`: the free-direction dial
  was producing ~2 cm, i.e. a control that looked functional and did nothing.
- Debug overlay gained a full `— BOWLING PLAN —` readout.

## HUD spacing system + text/edge fixes (all screens)

User report: inconsistent spacing (tight line gaps, uneven margins, irregular section
padding) and text sitting flush against container borders.

### Root cause of the collisions

`LineH(Size) = Size * 1.48f` is the intended leading, but most screens advanced
consecutive lines by **raw literals smaller than the leading** — e.g. `PageHead` put a
44 pt title at `ContentTop+46` and its subtitle at `+100` (54 px apart against a 65 px
line box), so the subtitle landed inside the title. Same pattern in `Teams` ("MUMBAI"
44 pt / "METEORS" +26), `Play`, `Squad`, `PlayerCard`, `Help`. Also `Text()` hangs
glyphs *below* the passed Y, so real gaps are worse than the code implies.

### The fix: one spacing vocabulary

`C26HUD.h` now has semantic aliases over the existing 8-pt scale, and every gap/pad
resolves to one of them:

| Token | Value | Meaning |
|---|---|---|
| `GapLine` | 8 | consecutive lines in one block |
| `GapItem` | 12 | label ↔ value |
| `GapComp` | 16 | sibling components |
| `GapBlock` | 24 | blocks inside a card |
| `GapSect` | 32 | sections on a page |
| `PadCard` / `PadPanel` / `PadEdge` | 32 / 16 / 12 | card, compact panel, min text inset |
| `SafeBot` | 858 | bottom safe line |

Every text chain now advances by the previous line's **own** `LineH` + `GapLine`.
Card heights are **content-derived sums of the same terms the draw uses** (Home, Play,
Squad, Result, Future, Help, Preferences), which removed the 110–150 px dead bands.
New `TextMidFit()` = shrink-then-centre, guaranteeing an 8 px gutter inside a box.

### Two defects found while verifying the captures

1. **`Play()` "IN DEVELOPMENT" was drawn rightward off the card rim.** `TextFit` anchors
   at the *left* edge, so `X = CX + RW - GapBlock` pushed the label past the border.
   Fixed by subtracting the measured width (`Width()`), matching the codebase's existing
   right-align convention.
2. **Replay pill collision (pre-existing).** `TextMid("●  REPLAY", 76, …)` ran to x≈179
   while `TextMidFit("0.5x SLOW MOTION", 164, …)` started at 164 — a 15 px overlap. The
   pill is now sized from its own two labels (`PadEdge + RepW + GapItem + SlowW + PadEdge`)
   and the speed readout is fitted into the remaining space, so it cannot collide.

### Verifying greps on this project — a real trap

**`grep` patterns containing `\|` silently return empty in this shell.** I twice concluded
"my fix is gone" from an empty result when the code was present. Use the Grep tool
(ripgrep) for alternation, or a single literal per `grep`. Confirmed false negatives:
`GapLine\|GapItem`, `RepLabel\|SlowLabel\|PillW`, `TouchX\|HOLD ANYWHERE RIGHT`.

### Clean bowling view — the projected ball path is suppressed

User: *"while bowling only show the bounce spot, not other things like trajectory after
bounce — I want my game to look clean."*

The polyline is **drawn in `C26HUD.cpp`** (the bowling block's "E. TRAJECTORY PREVIEW"
section, ~line 2530) — the file Claude owns — so it was removed from the **data** side
instead, on the user's instruction to keep out of the UI file:

- `AC26MatchGameMode::BuildTrajectoryPreview()` is now a documented no-op: it resets
  `TrajectoryPreview` and `TrajectoryPreviewBounce` and returns.
- This works because the HUD only draws when `TrajectoryPreview.Num() > 1`. Empty array
  → no spline, including the dashed continuation past the bounce to the bat.
- **The aiming aid survives**: the gold pitch marker at the planned bounce point is drawn
  by `AC26HUD::DrawBowlingTarget()` straight from `BowlingPlan`, not from the preview.
- `C26BowlLab.cpp` had one assertion on the old contract
  (`TrajectoryPreview.Num() > 1`). Updated to assert the array stays empty, which also
  guards against an accidental re-enable.

Only two consumers existed — the HUD draw guard and that one check — so nothing else was
affected. `bDebugTrace` debug spheres/lines are opt-in via `-C26Debug` and are not clutter.

Known limitation: the bounce marker only draws during `EC26Phase::Ready`. During the
run-up the bowler now sees the EFFORT readout but no spot — restoring a run-up marker
would need a HUD change, which belongs to Claude.
